# cmem2_API v2.14.0 — Changements visibles côté client

Date : 2026-08-04

## BREAKING CHANGES

Aucun. Tous les champs ajoutés sont optionnels et valent `null` par défaut ; un client qui ignore
le chiffrement continue de fonctionner à l'identique.

## Ce que la version apporte

Le chiffrement de bout en bout, entamé en interne, est maintenant disponible sur les **trois**
entités prévues au périmètre v1 : **journaux**, **tâches** et **contacts**.

Le modèle est le même partout : le client chiffre (PBKDF2-SHA256 pour la dérivation, AES-GCM 256
pour le contenu), l'API stocke et restitue des octets opaques. **Aucune clé, aucune passphrase,
aucun code de secours ne transite vers le serveur** — si l'API en reçoit un, c'est un bug client.

## 1. Métadonnées de clé — `/users/me/e2e-key`

Trois endpoints, authentifiés par le JWT existant, de portée owner-strict.

| Méthode | Effet |
| - | - |
| `GET /users/me/e2e-key?app_id=` | Récupère les métadonnées. `404` = chiffrement jamais activé, état normal |
| `PUT /users/me/e2e-key` | Crée (`201`) ou remplace (`200`) — activation, changement de passphrase, régénération du code de secours |
| `DELETE /users/me/e2e-key?app_id=` | Supprime les métadonnées |

Le serveur conserve : le sel PBKDF2 (public par conception), le nombre d'itérations, la clé
maîtresse enveloppée deux fois (par la passphrase et par le code de secours) et un vérificateur
chiffré. `wrapped_key_recovery` est optionnel — `null` si l'usager a refusé le code de secours.

`app_id` est **toujours transmis par le client** : aucun défaut serveur.

⚠️ `DELETE` ne supprime aucun contenu, mais rend illisible tout ce qui est chiffré. À traiter comme
une opération destructrice dans l'interface.

Bornes : `wrapped_*` et `verifier` ≤ 4 096 caractères, `kdf_salt` ≤ 64, `kdf` ≤ 32,
`kdf_iterations` entier strictement positif. Un dépassement renvoie `400` sans rien écrire.

## 2. Journaux (VJOURNAL) et tâches (VTODO) — `enc_alg` / `enc_iv`

Deux champs optionnels, acceptés sur `POST` et `PUT`/`PATCH`, restitués par tous les `GET`
(détail, liste, corbeille).

| Champ | Type | Rôle |
| - | - | - |
| `enc_alg` | string, max 32 | Algorithme, ex. `AES-GCM-256`. `null` = contenu en clair |
| `enc_iv` | string, max 32 | Vecteur d'initialisation base64 |

Quand `enc_alg` est renseigné, les champs chiffrés sont :

| Entité | Champs chiffrés |
| - | - |
| Journal | `summary`, `description` |
| Tâche | `title`, `description` |

**Règle de non-transformation** : ces champs traversent l'API sans `strip_tags`,
`htmlspecialchars`, purificateur HTML ni normalisation d'espaces. Un seul octet modifié rendrait le
contenu définitivement indéchiffrable.

**Longueurs** : le base64 gonfle d'environ 4/3, donc `summary` et `title` acceptent jusqu'à 2 000
caractères, `description` jusqu'à 16 000 000.

**Métadonnées restées en clair**, et pleinement exploitables :

| Entité | En clair |
| - | - |
| Journal | `dtstart`, `status`, `categories`, `related_to`, `url`, `uid`, horodatages |
| Tâche | `due`, `dtstart`, `status`, `priority`, `percent_complete`, `categories`, `recurrence_rule`, `uid` |

Le Gantt, le Kanban, les échéances et les rappels push s'appuient dessus.

**Retour au clair** : envoyer `enc_alg: null` et `enc_iv: null` explicitement. Omettre les champs
les laisse inchangés.

**Nouveau verbe** : `PATCH /calendars/{id}/todos/{todoId}` est désormais accepté, à parité avec
`PUT` (il n'existait pas). Comme pour les journaux, les deux verbes ne modifient que les champs
présents dans le corps.

## 3. Contacts — `enc_payload`

Les contacts ne suivent pas le même modèle : `courriels`, `telephones`, `adresses`, `sites` et
`reseaux` sont des colonnes structurées et validées, où un blob base64 ferait échouer la
validation. D'où un champ dédié.

| Champ | Type | Rôle |
| - | - | - |
| `enc_alg` | string, max 32 | Algorithme. `null` = contact en clair |
| `enc_iv` | string, max 32 | Vecteur d'initialisation base64 |
| `enc_payload` | string, max 16 000 000 | Base64 opaque : JSON chiffré des champs sensibles |

Le client y place le JSON chiffré de : `organisation`, `fonction`, `courriels`, `telephones`,
`adresses`, `sites`, `reseaux`, `notes`, `anniversaire`, `motif_relance` — et envoie les colonnes
structurées correspondantes **vides** (`null` ou `[]`). Aucun `422` n'est renvoyé pour cette raison.

Restent **en clair** (décision « C2 », pour garder tri et pagination côté serveur) : `prenom`,
`nom`, `categories`, `favori`, `photo_file_id`, `partage_scope`, `cree_le`, `maj_le`,
`date_relance`, `relance_faite_le`.

`enc_payload` est opaque : ni normalisation, ni troncature. Un dépassement de la borne renvoie
`400` — **jamais** une troncature silencieuse, qui rendrait la fiche indéchiffrable.

### Conséquence sur la recherche

`GET /contacts?q=` cherche désormais aussi dans `categories`. Sur une fiche chiffrée,
`organisation` et `courriels` sont vides côté serveur : la recherche s'y réduit d'elle-même à
`prenom` / `nom` / `categories`.

```txt
GET /contacts?q=tremblay        → la fiche chiffrée est trouvée (nom en clair)
GET /contacts?q=camille@ex.com  → elle n'est PAS trouvée — comportement attendu, pas d'erreur
```

Le complément de recherche (courriel, notes, organisation) est à faire côté client, après
déchiffrement.

### Conséquence sur l'import / export

- L'export `.vcf` d'une fiche chiffrée n'émet que les champs en clair : jamais de base64 dans
  `EMAIL`, `ORG` ou `NOTE`.
- À l'import vCard/CSV, une fiche existante **chiffrée** est ignorée (comptée dans `ignores`)
  plutôt qu'écrasée : la fusionner produirait une fiche mi-claire mi-chiffrée, indéchiffrable.
- La sauvegarde complète déchiffrée reste la responsabilité du client (export ZIP de compte).

## 4. Rappels push

Inchangés : ils utilisaient déjà un libellé générique. Un rappel portant sur une tâche ou une fiche
chiffrée n'expose ni le titre, ni le nom, ni le blob.

## Contrat inchangé pour un client non chiffrant

Un client qui n'envoie aucun champ `enc_*` obtient exactement le comportement de la v2.13.0 :
`enc_alg`, `enc_iv` et `enc_payload` valent `null` et les contenus restent en clair.
