# cmem2_API v2.13.0 — Changements visibles côté client

Date : 2026-08-03

## BREAKING CHANGES

Aucun changement de contrat rompant une intégration existante. Deux changements de
**comportement** méritent toutefois une vérification côté client.

### 1. `mime_type` et `media_type` proviennent maintenant du fichier, pas du client

Avant, `POST /files` enregistrait le `Content-Type` envoyé par le client, sans le vérifier. Un
client qui envoyait `application/octet-stream` (valeur par défaut de plusieurs bibliothèques HTTP)
faisait ranger une image en `media_type = executable`.

Le type enregistré est désormais lu dans la signature du fichier.

| Client | Effet |
| - | - |
| Envoie déjà le bon `Content-Type` | Aucun changement |
| Envoie `application/octet-stream` | `media_type` se corrige (souvent `executable` → `image`) |

**Les fichiers déjà en base conservent leur ancien `mime_type`** — aucune reprise de données n'a
été faite. Un client qui filtre sur `media_type` peut donc voir des fichiers antérieurs mal
classés. Demander une migration si nécessaire.

### 2. Un SVG n'est plus rendu inline

`GET /files/{id}` sert un `image/svg+xml` avec `Content-Disposition: attachment` et
`X-Content-Type-Options: nosniff`. Une page qui pointait un `<img src="/files/{id}">` vers un SVG
déclenchera un téléchargement au lieu d'un affichage.

**Remplacement** : `GET /files/png-from-svg?id={id}&width=...` — déjà disponible, inchangé.

Les autres `image/*` gardent l'affichage inline et le cache immuable d'un an.

## Validation d'upload — ce qui passe et ce qui ne passe plus

La validation croise l'**extension** et la **signature réelle** du fichier ; les deux doivent
concorder.

**Ne passe plus** : un fichier renommé pour tromper la validation. Un script texte renommé `.png`,
une archive renommée `.png`, ou un binaire inconnu sous une extension d'image ou de document sont
refusés. Un MIME générique n'est accepté que pour les extensions dont c'est la signature attendue :

| MIME détecté | Extensions acceptées |
| - | - |
| `application/zip` | `docx`, `xlsx`, `pptx`, `odt`, `ods`, `odp`, `zip` |
| `text/plain` | `txt`, `csv`, `md`, `rtf`, `svg`, `gpx` |
| `application/octet-stream` | `exe`, `msi`, `zip`, `7z` |

**Passe maintenant** : `pptx`, `odt`, `ods`, `odp`, `csv`, `md`, `rtf`, `heic`, `heif`, `avif`,
`tiff`, `tif`. Ces formats étaient refusés par la liste d'extensions alors que leur type réel était
déjà admis.

## Codes de refus

`POST /files` répond `400` avec un code stable dans `errors.code` — plus besoin d'analyser le
message français :

| Motif | `errors.code` | Données jointes |
| - | - | - |
| Type non autorisé | `FILE_TYPE_REFUSED` | `detected_type`, `extension` |
| Taille dépassée | `FILE_TOO_LARGE` | `max_size_bytes`, `file_size_bytes` |

`PATCH /files/{id}` ajoute `FILE_NAME_INVALID`.

## Nouveaux endpoints

### `PATCH /files/{id}` — renommer

```http
PATCH /files/42
Authorization: Bearer {jwt}
Content-Type: application/json

{ "original_name": "Devis 2026 révisé.pdf", "description": "Version signée" }
```

Les deux champs sont optionnels, au moins un requis (sinon `400`). `original_name` : non vide,
255 caractères au plus, sans `/`, `\` ni `..`. Le fichier stocké (`file_name`, `url`) ne bouge pas.
Propriétaire ou administrateur.

### `GET /files/{id}/tags` — étiquettes

```json
{ "file_id": 42, "tags": [ { "id": 7, "name": "Contrats", "color": "#33aa55" } ] }
```

Chaque ligne de `GET /files/user/{user_id}` porte aussi un champ `tags`, chargé en une seule
requête pour toute la page — inutile d'interroger l'API fichier par fichier.

Association / dissociation inchangée : `PUT /tags/{tag_id}/{file_id}` avec
`table_associate: files`.

## Plafond d'upload

Porté de 20 Mo à **100 Mo** (`FILES_MAX_UPLOAD_MB`). Les limites par catégorie restent en vigueur :
image 10 Mo, document 10 Mo, audio 20 Mo, vidéo 50 Mo, exécutables et archives 200 Mo — plafonnées
par les 100 Mo.

Les clients qui bloquent l'envoi côté navigateur peuvent relever leur propre constante à
`100 * 1024 * 1024`.
