# v2.19.0 — Changements visibles client

## BREAKING CHANGES

### Accès sur approbation

Tout nouveau compte (`POST /users/register` ou OTP `POST /auth/send-code`) est créé
**en attente** : `access_status = pending`. Les comptes existants à la mise à jour sont
approuvés (`approved`).

Un compte `pending` ou `suspended` se connecte normalement et reçoit son JWT, mais toute
route JWT répond `403`, sauf :

| Route | Ouverte à |
| - | - |
| `GET /auth/me` | `pending`, `suspended` |
| `POST /auth/logout` | `pending`, `suspended` |
| `DELETE /users/me` | `pending`, `suspended` |
| `GET /files/{id}`, `GET /files/{id}/info` (fichier `public` ou `grand-public`) | `pending` seulement |

```json
{
  "success": false,
  "message": "Compte en attente d'approbation",
  "errors": {
    "code": "ACCOUNT_PENDING",
    "message": "Ce compte doit être approuvé par un administrateur avant d'utiliser l'application."
  }
}
```

`errors.code` vaut `ACCOUNT_PENDING` ou `ACCOUNT_SUSPENDED`. Le client affiche un écran
d'attente (ou « compte suspendu ») avec déconnexion, sans réessayer en boucle.

`access_status` est renvoyé dans `data.user` de `POST /auth/login`, `POST /auth/verify-code`,
`POST /auth/refresh`, et dans `GET /auth/me`.

Clients prévenus : directives cmem_web #417, jdb #418, XMGame #419.

### Modules cochés par personne

La disponibilité d'un module (`available`) ne dépend plus du plan Stripe ni du plan « ami » :
elle vient des modules cochés par l'administrateur pour chaque compte.

- `GET /modules` : même forme. `available` = modules cochés du compte ∪ ceux des
  propriétaires de ses groupes actifs. Le champ `plan` reste renvoyé mais ne décide plus rien.
- `GET/PATCH /groups/{id}/modules` : `available` = modules cochés du propriétaire du groupe.
- Module non coché : `403 MODULE_NOT_AVAILABLE` sur `PATCH /modules/{key}`,
  `POST /ai/summarize` et `PUT /booking/page` (activation). Afficher « non activé par
  l'administrateur », plus d'invite à l'upgrade.

Aucun module retiré aux comptes existants : leurs modules sont dérivés de leur plan actuel.

Client prévenu : directive cmem_web #422.

## Ajouté

### Administration (ADMINISTRATEUR ou plus)

| Méthode | Route | Description |
| - | - | - |
| PUT | `/users/{id}/access-status` | `{"status": "pending" \| "approved" \| "suspended"}` |
| GET | `/users?access_status=pending` | Filtre par statut ; `access_status` sur chaque entrée |
| POST | `/invitations` | `{"email", "modules"?, "ai_budget_usd"?, "expires_in_days"?}` → `201` |
| GET | `/invitations` | Liste, `status` = `pending` / `accepted` / `expired` |
| DELETE | `/invitations/{id}` | Supprime une invitation |
| GET | `/users/{id}/modules` | Modules cochés du compte |
| PUT | `/users/{id}/modules` | `{"modules": [...]}` remplace la liste |

- Première approbation : modules par défaut `projet`, `contacts`, `crm`, `ged`.
- Courriel invité : compte approuvé à la création, à la connexion, ou dès l'invitation si le
  compte existe déjà ; modules et budget IA de l'invitation appliqués.
- Courriels : l'admin est notifié à chaque inscription en attente ; l'usager est notifié à
  son approbation.

OTP fixe que `e2e@test.local`. Inactifs en production.
