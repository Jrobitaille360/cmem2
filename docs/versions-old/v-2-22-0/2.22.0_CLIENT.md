# v2.22.0 — Changements visibles client

Rappels unifiés (contrat cmem_web #236, directive #487) : un rappel = un canal (`EMAIL` ou
`DISPLAY`) + un délai. Trois niveaux : défaut par type, liste par élément, filtre par
appareil. Un seul cron envoie courriels et push. Référence complète :
`docs/docs-api/ics/GUIDE.md` § « Rappels unifiés ».

## BREAKING CHANGES

### `REMINDER_CHANNEL_UNSUPPORTED` retiré

`DISPLAY` est accepté et envoyé (push). Écriture de `notifications` validée par des `422`
codés, `errors = { code, field, message }` :

| Code | Cas | `field` |
| - | - | - |
| `REMINDER_CHANNEL_UNKNOWN` | `type` hors `EMAIL` / `DISPLAY` (`notification`, `AUDIO` refusés en écriture) | `notifications.{i}.type` |
| `REMINDER_LEAD_INVALID` | délai non entier ou hors `0..40320` | `notifications.{i}.minutes_before` |
| `REMINDER_DUPLICATE` | même `type` + délai deux fois | `notifications.{i}` |
| `REMINDER_TOO_MANY` | plus de 10 rappels | `notifications` |

`email` / `display` en minuscules sont acceptés et normalisés en majuscules.

### `notifications` relu sous forme normalisée

`[{ "type": "EMAIL" | "DISPLAY", "minutes_before": n }]` ou `null`, partout : détail,
**listing `GET /calendars/{id}/events`** (renvoyait la chaîne JSON brute) et expansion des
occurrences. Les formes héritées (`notification`, `AUDIO`, clé `minutes`) sont converties.

### Sémantique du champ (toutes les entités)

| Valeur envoyée | Effet |
| - | - |
| absent | Création : défaut du type. Mise à jour : inchangé. |
| `null` | Défaut du type. |
| `[]` | Aucun rappel. |
| `[...]` | Remplace le défaut du type. |

### Courriel de rappel

Titre générique par défaut (titre réel seulement avec `show_entity_detail` du type, jamais
pour une fiche chiffrée), envoyé à l'adresse du compte (`notification_email` n'est plus lu),
soumis à la plage silencieuse du type. `GET /notifications/email` est déprécié : l'ancienne
file n'est plus traitée.

### Journal d'envoi par appareil

Un appareil réabonné reçoit les rappels encore dans la tolérance qu'il n'avait pas reçus.

## Ajouté

| Route / champ | Effet |
| - | - |
| `notifications` sur `POST\|PUT /calendars/{id}/todos[/{id}]` | Rappels d'une tâche (`due`) |
| `notifications` sur `POST /projets/projects/{id}/tasks`, `PATCH /projets/tasks/{id}` | Rappels d'une tâche de projet (date seule : 00:00 fuseau usager) |
| `notifications` sur `POST\|PUT /contacts[/{id}]` | Rappels de la relance (`date_relance`) |
| `notifications` sur `POST /contacts/{id}/opportunites`, `PUT /opportunites/{id}` | Rappels de la clôture prévue |
| `GET\|PUT /notifications/defaults?app_id=` | Défauts par type (`event`, `recurring`, `task_due`, `contact_followup`) |
| `GET /notifications/devices?app_id=`, `PUT\|DELETE /notifications/devices/{id}` | Appareils : `kinds`, plage silencieuse, libellé ; `endpoint_hash` pour repérer l'appareil courant |

Défauts : délais `0, 5, 10, 15, 30, 60, 120, 1440, 2880` seulement. Liste par élément :
`0..40320`. `app_id` obligatoire sur `/notifications/defaults` et `/notifications/devices`.

Codes `422` supplémentaires (non nommés par le contrat) : `APP_ID_REQUIRED`,
`DEFAULTS_REQUIRED`, `REMINDER_KIND_UNKNOWN`, `QUIET_TIME_INVALID`, `QUIET_RANGE_INCOMPLETE`.

## Corrigé

- Les rappels des tâches de projet sont envoyés (courriel + push) — #439.
- `GET|PUT /users/me/notification-preferences` atteignent enfin leur contrôleur (étaient
  capturés par `/users/me`) : désactiver les courriels de rappel a maintenant un effet.

## Déprécié (retiré en v2.23.0)

- `rappelMinutesAvant` (tâches de projet) : `n` → `[EMAIL n, DISPLAY n]`, ignoré si
  `notifications` est fourni ; relu = premier délai de la liste.
- `GET|PUT /push/preferences` : projection des défauts `DISPLAY` de `/notifications/defaults`.
- `GET /notifications/email`.

## Écarts au contrat #236

- Tâches : la route réelle est `/calendars/{id}/todos`, pas `/tasks`.
- Migration : les comptes sans préférence push gardent des appareils à `kinds` = les 4 types
  (au lieu de `[]`) ; leurs défauts sont vides, donc aucun push — même effet.
