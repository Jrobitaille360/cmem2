# Déploiement production — v2.2.1

Checklist à suivre dans l'ordre pour mettre en production la version 2.2.1.

> **v2.2.1 couvre Phase 2 (VEVENT enrichi), Phase 3 (ATTENDEE/ORGANIZER/iTIP),
> Phase 4 (EXDATE/RDATE/RELATED-TO/VALARM/DURATION) et Phase 5 (VTODO/VJOURNAL/VFREEBUSY).**
> Quatre migrations SQL sont requises.

---

## 1. Migrations SQL

**Quatre migrations SQL sont requises pour cette version — exécuter dans l'ordre.**

### 1a. Phase 2 — propriétés VEVENT

```bash
mysql -u <user> -p <database> < docs/docs_ICS/migrations/20260331_ph2_vevent_props.sql
```

Ce script ajoute 7 colonnes à la table `calendar_events` :

| Colonne | Type | Défaut |
| :--- | :--- | :--- |
| `priority` | `TINYINT(1) UNSIGNED NOT NULL` | `0` |
| `class` | `ENUM('PUBLIC','PRIVATE','CONFIDENTIAL') NOT NULL` | `PUBLIC` |
| `transp` | `ENUM('OPAQUE','TRANSPARENT') NOT NULL` | `OPAQUE` |
| `categories` | `JSON NULL` | `NULL` |
| `geo_lat` | `DECIMAL(10,7) NULL` | `NULL` |
| `geo_lng` | `DECIMAL(10,7) NULL` | `NULL` |
| `attachments` | `JSON NULL` | `NULL` |

### 1b. Phase 3 — ORGANIZER

```bash
mysql -u <user> -p <database> < docs/docs_ICS/migrations/20260401_ph3_organizer.sql
```

Ce script ajoute 2 colonnes à la table `calendar_events` :

| Colonne | Type | Défaut |
| :--- | :--- | :--- |
| `organizer_email` | `VARCHAR(255) NULL` | `NULL` |
| `organizer_name` | `VARCHAR(255) NULL` | `NULL` |

### 1c. Phase 4 — récurrence avancée

```bash
mysql -u <user> -p <database> < docs/docs_ICS/migrations/20260401_ph4_recurrence.sql
```

Ce script ajoute 3 colonnes à la table `calendar_events` :

| Colonne | Type | Défaut |
| :--- | :--- | :--- |
| `rdate` | `TEXT NULL` | `NULL` |
| `related_to` | `VARCHAR(255) NULL` | `NULL` |
| `duration` | `VARCHAR(20) NULL` | `NULL` |

### 1d. Phase 5 — composants CalDAV additionnels

```bash
mysql -u <user> -p <database> < docs/docs_ICS/migrations/20260401_ph5_components.sql
```

Ce script crée 2 nouvelles tables :

| Table | Description |
| :--- | :--- |
| `calendar_todos` | VTODO — tâches (id, uid, calendar_id, user_id, title, status, due, priority…) |
| `calendar_journals` | VJOURNAL — journaux (id, uid, calendar_id, user_id, summary, dtstart, status…) |

> Toutes les migrations utilisent `ADD COLUMN` ou `CREATE TABLE IF NOT EXISTS` —
> les lignes existantes reçoivent les valeurs par défaut sans interruption de service.

## 2. Variables d'environnement

**Aucune variable d'environnement nouvelle requise pour cette version.**

Le `.env` de production issu de la v2.2.0 est compatible sans modification.

---

## 3. Déploiement du code

```bash
git fetch origin
git reset --hard origin/main
composer install --no-dev --optimize-autoloader
```

> `reset --hard` n'affecte pas les fichiers ignorés par git (`.env`, logs, `private/`, etc.).

### Prérequis côté client

La v2.2.1 ne contient **aucun changement cassant**.
Les clients en v2.2.0 continuent de fonctionner sans modification.

Les nouveaux champs sont documentés dans `docs/2.2.1_CLIENT.md` (Ph2–Ph5).

## 4. Vérifications post-déploiement

### Phase 2

```text
POST /calendars/{id}/events  (priority=1, class=PRIVATE, transp=OPAQUE)
  → 201, champs retournés dans la réponse

GET  /calendars/{id}/events/{eventId}
  → 200, priority/class/transp/categories présents

GET  /calendars/{id}/ics
  → 200, contenu ICS contient PRIORITY, CLASS, TRANSP, CATEGORIES, GEO, URL, ATTACH

POST /calendars/{id}/events  (priority=99)
  → 400 (validation)

POST /calendars/{id}/events  (class=UNKNOWN)
  → 400 (validation)

POST /calendars/{id}/events  (geo_lat sans geo_lng)
  → 400 (validation)
```

### Phase 3

```text
POST /calendars/{id}/events  (attendees=[{email, name, role, partstat, rsvp, cutype}], organizer_email, organizer_name)
  → 201, champs attendees/organizer_email/organizer_name retournés

GET  /calendars/{id}/ics
  → 200, contenu ICS contient ATTENDEE;CN=...;ROLE=...;PARTSTAT=...;RSVP=... et ORGANIZER;CN=...

POST /notifications/attendee-reply  (event_id, attendee_email, partstat=ACCEPTED)
  → 200, { event_id, attendee_email, partstat: "ACCEPTED" }

POST /notifications/attendee-reply  (partstat=INVALIDE)
  → 400 (validation)

POST /calendars/{id}/events  (attendees=[{name: "Sans email"}])
  → 400 (attendee sans email)
```

### Phase 4

```text
POST /calendars/{id}/events  (duration=PT1H30M, sans end_datetime)
  → 201, duration retourné dans la réponse

GET  /calendars/{id}/ics
  → 200, ICS contient DURATION:PT1H30M (pas de DTEND)

POST /calendars/{id}/events  (duration=PT1H + end_datetime)
  → 400 (exclusivité duration/end_datetime)

POST /calendars/{id}/events  (duration=1H30)  -- format invalide
  → 400 (validation)

POST /calendars/{id}/events  (rdate="2026-10-08 09:00:00,2026-10-15 09:00:00")
  → 201, rdate présent dans la réponse

GET  /calendars/{id}/ics
  → 200, ICS contient RDATE

DELETE /calendars/{id}/events/{eventId}/occurrences  (scope=only_this)
  → 200, occurrence annulée

GET  /calendars/{id}/ics
  → 200, ICS contient EXDATE

GET  /calendars/{id}/ics  (event avec notifications)
  → 200, ICS contient BEGIN:VALARM ... TRIGGER:-PT{n}M
```

### Phase 5

```text
POST /calendars/{id}/todos  (title)
  → 201, todo object retourné

GET  /calendars/{id}/todos
  → 200, liste todos

PUT  /calendars/{id}/todos/{todoId}  (status=COMPLETED, percent_complete=100)
  → 200

GET  /calendars/{id}/ics
  → 200, ICS contient BEGIN:VTODO

POST /calendars/{id}/todos  (sans title)
  → 400 (validation)

POST /calendars/{id}/journals  (summary)
  → 201, journal object retourné

GET  /calendars/{id}/journals
  → 200, liste journals

GET  /calendars/{id}/ics
  → 200, ICS contient BEGIN:VJOURNAL

POST /calendars/{id}/journals  (sans summary)
  → 400 (validation)

GET  /calendars/{id}/freebusy?start=YYYY-MM-DD&end=YYYY-MM-DD
  → 200, { freebusy: [...], calendar_id, period }

GET  /calendars/{id}/freebusy  (start > end)
  → 400 (validation)
```

## Rollback

Toutes les migrations sont additives (`ADD COLUMN`, `CREATE TABLE IF NOT EXISTS`).
Un retour au tag v2.2.0 ne nécessite pas d'annuler les migrations —
les colonnes et tables supplémentaires sont ignorées par le code v2.2.0.

Si une annulation complète est nécessaire :

```sql
-- Retrait Phase 4
ALTER TABLE calendar_events
    DROP COLUMN rdate,
    DROP COLUMN related_to,
    DROP COLUMN duration;

-- Retrait Phase 3
ALTER TABLE calendar_events
    DROP COLUMN organizer_email,
    DROP COLUMN organizer_name;

-- Retrait Phase 2
ALTER TABLE calendar_events
    DROP COLUMN priority,
    DROP COLUMN class,
    DROP COLUMN transp,
    DROP COLUMN categories,
    DROP COLUMN geo_lat,
    DROP COLUMN geo_lng,
    DROP COLUMN attachments;

-- Retrait Phase 5
DROP TABLE IF EXISTS calendar_todos;
DROP TABLE IF EXISTS calendar_journals;
```

Puis retour au code :

```bash
git reset --hard v2.2.0
composer install --no-dev --optimize-autoloader
```
