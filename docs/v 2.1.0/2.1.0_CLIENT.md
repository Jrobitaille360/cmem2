# Migration client — v2.0.0 → v2.1.0

Ce document liste les changements que les applications clientes doivent prendre en compte
avant de consommer l'API en version 2.1.0.

---

## Changements cassants

### Pagination — clé `limit` → `per_page`

#### Endpoints affectés

| Endpoint | Changement |
| :--- | :--- |
| `GET /users` | `limit` absent, remplacé par `per_page` |
| `GET /groups/public` | `limit` absent, remplacé par `per_page` |
| `GET /groups/search` | `limit` absent, remplacé par `per_page` |
| `GET /users/{id}/groups` | `limit` absent, remplacé par `per_page` |

#### Avant (2.0.0)

```json
{
  "data": { "users": [...], "total": 42, "page": 1, "limit": 20 }
}
```

#### Après (2.1.0)

```json
{
  "data": {
    "users": [...],
    "total": 42,
    "page": 1,
    "per_page": 20,
    "total_pages": 3
  }
}
```

**Action requise** : remplacer toute lecture de `data.limit` par `data.per_page`.
`total_pages` est maintenant toujours présent — plus besoin de le calculer côté client.

---

### Rotation du device token après `POST /auth/refresh`

**Avant (2.0.0)** : le `device_token` restait stable d'un refresh à l'autre.

**Après (2.1.0)** : chaque `POST /auth/refresh` réussi génère un **nouveau** `device_token`
et révoque l'ancien immédiatement.

**Action requise** : après chaque refresh, persister la valeur de `device_token` retournée
dans la réponse et jeter l'ancienne.

```json
POST /auth/refresh
→ 200 {
    "jwt": "eyJ...",
    "device_token": "NOUVEAU_TOKEN_64_CHARS"
  }
```

Si le client envoie un `device_token` révoqué, le serveur retourne `401`.

---

### Rate limiting sur `POST /auth/login` et `POST /auth/send-code`

Après **5 tentatives échouées** sur la même combinaison email + IP dans une fenêtre de
10 minutes, le serveur répond `429 Too Many Requests`.

```json
429 {
  "error": "RATE_LIMIT_EXCEEDED",
  "message": "Trop d'échecs consécutifs. Réessayez dans 10 minutes."
}
```

**Action requise** : gérer le code `429` dans le flux de connexion — afficher un message
d'attente et ne pas réessayer immédiatement.

---

### Logout révoque le token côté serveur

**Avant (2.0.0)** : `POST /auth/logout` ne faisait que signaler la déconnexion.
Le token restait techniquement valide jusqu'à son expiration.

**Après (2.1.0)** : le `jti` du token est ajouté à la blacklist JWT dès le logout.
Toute requête ultérieure avec ce token reçoit `401`, même si le token n'est pas expiré.

**Action requise** : aucune — le comportement est plus sécurisé.
Continuer à supprimer le token côté client après logout.

---

## Nouveautés (non cassantes)

### `GET /auth/me` — profil utilisateur

Retourne les données de l'utilisateur authentifié à jour depuis la base de données.
Requiert un JWT valide dans le header `Authorization: Bearer {jwt}`.

```http
GET /auth/me
Authorization: Bearer eyJ...
```

```json
200 {
  "message": "Profil utilisateur",
  "data": {
    "user": {
      "id": 1,
      "name": "Alice",
      "email": "alice@example.com",
      "role": "UTILISATEUR",
      "email_verified": 1,
      "last_login": "2026-03-25 18:00:00",
      ...
    }
  }
}
```

Le champ `password_hash` est absent de la réponse.
