# Déploiement production — v2.2.0

Checklist à suivre dans l'ordre pour mettre en production la version 2.2.0.

---

## 1. Migrations SQL

**Aucune migration SQL requise pour cette version.**

Les tables `jwt_blacklist` et `login_attempts` créées en v2.1.0 sont conservées sans modification.

---

## 2. Variables d'environnement

**Aucune variable d'environnement nouvelle requise pour cette version.**

Le `.env` de production issu de la v2.1.0 est compatible sans modification.

---

## 3. Déploiement du code

```bash
git fetch origin
git reset --hard origin/main
composer install --no-dev --optimize-autoloader
```

> `reset --hard` n'affecte pas les fichiers ignorés par git (`.env`, logs, `private/`, etc.).

### Prérequis côté client

**Ne pas déployer avant que le client ait mis à jour son application.**
La v2.2.0 contient des changements cassants documentés dans `docs/2.2.0_CLIENT.md` :

- Réponses fichiers : `data.file_id` → `file.id`, enveloppe `data` → `file`
- Réponses utilisateurs : `data` → `user` ; DELETE/restore retournent `{ deleted/restored: true }`
- Tags : `PUT /tags/{tag_id}/{item_id}` — paramètre `table` → `table_associate`, champ `action` retiré
- `GET /stats/users/{id}` — désormais admin uniquement ; utiliser `GET /stats/my-stats` à la place
- `POST /auth/resend-verification` et `POST /users/password-change` — toujours `200` (anti-énumération)

---

## 4. Vérifications post-déploiement

```text
GET  /plans/1                   → 200 avec champ "plan" (ou 404 si aucun plan actif)
GET  /stats/my-stats            → 200 avec JWT valide, 401 sans
GET  /stats/users/{id}          → 403 avec token non-admin, 200 avec admin
GET  /users/me                  → 200, réponse { "user": { … } }
GET  /users/{id}                → 200, réponse { "user": { … } }
POST /files                     → upload OK, réponse { "file": { "id": …, … } }
POST /auth/resend-verification  → 200 quelle que soit l'adresse (message générique)
POST /users/password-change     → 200 quelle que soit l'adresse (message générique)
```

---

## Rollback

Aucune migration SQL à annuler pour cette version.
Un retour au tag v2.1.1 suffit :

```bash
git fetch origin
git reset --hard v2.1.1
composer install --no-dev --optimize-autoloader
```
