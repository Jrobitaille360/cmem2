# cmem2_API v2.13.0 — Checklist de déploiement production

Date : 2026-08-03
Cible : `cmem2.journauxdebord.com`

## 1. Migrations SQL

**Aucune migration dans cette release.** Le schéma est identique à la v2.12.0 — il n'y a donc pas
de `build_DB-v-2.13.0.sql` : utiliser `docs/v-2-12-0/build_DB-v-2.12.0.sql` pour une installation
neuve.

## 2. Variables `.env` à ajouter

```dotenv
APP_VERSION=2.13.0
# Plafond dur de POST /files en Mo (aligné sur upload_max_filesize)
FILES_MAX_UPLOAD_MB=100
```

`FILES_MAX_UPLOAD_MB` a une valeur par défaut de 100 dans `environment.php` : son absence ne
casse rien, mais la rendre explicite évite les surprises.

## 3. Fichiers de configuration serveur

| Fichier | Changement | Criticité |
| - | - | - |
| `.htaccess` | `upload_max_filesize 20M → 100M`, `post_max_size 25M → 105M` | **Requis** |
| `user.ini` / `.user.ini` | Inchangés (déjà à `100M`) | — |

Sans le `.htaccess` déployé, PHP continuera de refuser les envois de plus de 20 Mo **avant** que le
code ne les voie (`UPLOAD_ERR_INI_SIZE`) — le plafond applicatif de 100 Mo n'aurait aucun effet.

## 4. Déploiement

```powershell
.\private\deploy.ps1 -Target prod
```

Le script transfère `index.php`, `src/`, `.htaccess`, `composer.*`, puis exécute
`composer install --no-dev --optimize-autoloader` sur le serveur.

Si composer est cassé côté cPanel :

```powershell
.\private\deploy.ps1 -Target prod -LocalComposerInstall
```

## 5. Crons

Aucun changement de cron dans cette release.

## 6. Vérifications post-déploiement

```bash
# Version en ligne
curl -s https://cmem2.journauxdebord.com/health | grep -i version

# Plafond PHP effectif (doit indiquer 100M)
# → via un upload réel de plus de 20 Mo, voir ci-dessous
```

| # | Vérification | Attendu |
| - | - | - |
| 1 | `GET /health` | `200`, `APP_VERSION = 2.13.0` |
| 2 | `POST /files` avec un `.exe` de plus de 20 Mo | `201` (et non `400 — maximum 20 MB`) |
| 3 | `POST /files` avec un `.ods` ou un `.csv` | `201` |
| 4 | `POST /files` avec un fichier texte renommé `.png` | `400`, `errors.code = FILE_TYPE_REFUSED` |
| 5 | `GET /files/{id}` sur un SVG existant | En-tête `Content-Disposition: attachment` |
| 6 | `GET /files/{id}` sur un PNG existant | En-tête `Content-Disposition: inline` (non-régression) |
| 7 | `PATCH /files/{id}` avec `original_name` | `200`, `url` inchangée |
| 8 | `GET /files/user/{id}` | Chaque ligne porte un champ `tags` |

Pour rejouer la couverture complète contre la production, basculer
`private/destination.txt` sur `cmem` puis :

```bash
php private/tests/test_files_types.php
```

⚠️ Ces tests créent et suppriment des fichiers réels sur le compte de test — ne pas les lancer en
production sans le vouloir.

## 7. Suivi client

Prévenir les clients du changement de comportement `media_type` / SVG — voir
`docs/v-2-13-0/2.13.0_CLIENT.md`. Les fichiers **déjà en base** gardent leur ancien `mime_type` :
aucune reprise de données n'a été faite.

## 8. Retour arrière

Aucune migration à annuler. Redéployer le tag précédent suffit :

```bash
git checkout v2.12.0
powershell private/deploy.ps1 -Target prod
```

Attention : un retour arrière remet le `.htaccess` à `20M` et rétablit le rendu inline des SVG.
