# Déploiement production — v2.1.0

Checklist à suivre dans l'ordre pour mettre en production la version 2.1.0.

---

## 1. Migrations SQL

À exécuter **une seule fois** sur la base de données de production.
Les scripts sont idempotents (`CREATE TABLE IF NOT EXISTS`).

```bash
mysql -u <user> -p <database> < src/auth_groups/docs/20260325_A1_jwt_blacklist.sql
mysql -u <user> -p <database> < src/auth_groups/docs/20260325_A2_login_attempts.sql
```

| Script | Table créée | Pourquoi |
| :--- | :--- | :--- |
| `20260325_A1_jwt_blacklist.sql` | `jwt_blacklist` | Révocation JWT au logout (`jti`) |
| `20260325_A2_login_attempts.sql` | `login_attempts` | Rate limiting login / send-code |

---

## 2. Variables d'environnement

Ajouter dans `.env.auth_groups` (ou l'équivalent production) :

```dotenv
# Rate limiting authentification
RATE_LIMIT_AUTH_MAX_ATTEMPTS=5
RATE_LIMIT_AUTH_WINDOW_MINUTES=10
ENABLE_RATE_LIMITING=true

# Chemin de base de l'API dans l'URL
# Valeur actuelle dans le routeur — à ajuster si le vhost change
BASE_PATH=/cmem2_API
```

> Si `BASE_PATH` n'est pas défini, la valeur par défaut `/cmem2_API` est utilisée
> (comportement identique à la v2.0.0).

---

## 3. Cron — nettoyage quotidien

Ajouter l'entrée suivante dans `crontab -e` (serveur hébergeant l'API) :

```cron
0 2 * * * php /chemin/absolu/vers/src/cron/cleanup.php >> /chemin/absolu/vers/logs/cron.log 2>&1
```

Le script purge chaque nuit :

- `otp_codes` — codes expirés ou déjà utilisés
- `jwt_blacklist` — entrées dont `expires_at` est dépassé
- `login_attempts` — tentatives hors fenêtre de rate limiting

Vérification manuelle (doit s'exécuter sans erreur) :

```bash
php src/cron/cleanup.php
```

Sortie attendue :

```text
[2026-03-25 02:00:01] cleanup.php
  otp_codes : OK
  jwt_blacklist : OK — 0 supprimé(s)
  login_attempts : OK — 0 supprimé(s)
```

---

## 4. Déploiement du code

```bash
git pull origin main
composer install --no-dev --optimize-autoloader
```

Aucun changement de structure de fichiers existants — les nouvelles routes et
fonctionnalités sont ajoutées de manière non cassante pour le serveur.

---

## 5. Vérifications post-déploiement

```text
GET  /auth/me              → 401 sans JWT (attendu)
POST /auth/login           → login normal OK, puis 429 après 5 échecs
POST /auth/refresh         → nouveau device_token dans la réponse
POST /auth/logout          → token révoqué, requête suivante avec même token → 401
GET  /users?page=1         → réponse contient per_page et total_pages
GET  /groups/public        → réponse contient per_page et total_pages
```

---

## Rollback

En cas de problème, les migrations SQL sont les seuls changements irréversibles.
Les tables peuvent être supprimées si besoin :

```sql
DROP TABLE IF EXISTS jwt_blacklist;
DROP TABLE IF EXISTS login_attempts;
```

Le code v2.0.0 fonctionnera de nouveau correctement après rollback git.
