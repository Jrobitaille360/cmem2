# v2.19.1 — Changements visibles client

## Corrigé

### `device_id` non UUID à la connexion → `422`

`POST /auth/login`, `POST /auth/verify-code` et `POST /auth/restore-account/verify` : un
`device_id` fourni mais qui n'est pas un UUID (format `8-4-4-4-12`) répond maintenant `422`
avec `errors.device_id`, au lieu d'un `500 Erreur serveur`.

La vérification a lieu avant le mot de passe et le code OTP : le code n'est plus consommé par
une requête vouée à l'échec. Le client peut corriger le `device_id` et renvoyer le même code.

```json
{
  "success": false,
  "message": "Données invalides",
  "errors": { "device_id": "device_id doit être un UUID valide (format 8-4-4-4-12)." }
}
```

`device_id` absent ou vide : inchangé (connexion sans `device_token`).
`POST /auth/refresh` : inchangé (`401 INVALID_DEVICE_TOKEN` sur un `device_id` invalide).

## BREAKING CHANGES

Aucun. Un client qui envoyait un `device_id` non UUID recevait déjà une erreur (`500`) ; il
reçoit désormais un `422` explicite.
