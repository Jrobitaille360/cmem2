# Migration client — v2.2.0 → v2.2.1

> **v2.2.1 couvre Phase 2 (VEVENT enrichi) et Phase 3 (ATTENDEE/ORGANIZER/iTIP).**

Ce document liste les changements que les applications clientes doivent prendre en compte
avant de consommer l'API en version 2.2.1.

---

## Changements cassants

**Aucun changement cassant dans cette version.**

La v2.2.1 est rétrocompatible avec la v2.2.0.

---

## Nouveautés (non cassantes) — Propriétés VEVENT enrichies

### Champs disponibles sur `POST /calendars/{id}/events` et `PUT /calendars/{id}/events/{eventId}`

Les événements acceptent maintenant 7 nouveaux champs optionnels correspondant aux propriétés
RFC 5545 du composant VEVENT :

| Champ | Type | Valeurs / format | Propriété ICS | Défaut |
| :--- | :--- | :--- | :--- | :--- |
| `priority` | entier 0–9 | 0=non défini, 1=haute, 5=normale, 9=basse | `PRIORITY` | `0` |
| `class` | string | `PUBLIC` \| `PRIVATE` \| `CONFIDENTIAL` | `CLASS` | `PUBLIC` |
| `transp` | string | `OPAQUE` \| `TRANSPARENT` | `TRANSP` | `OPAQUE` |
| `categories` | tableau de strings | ex. `["Travail","Réunion"]` | `CATEGORIES` | `null` |
| `geo_lat` | décimal | -90 à 90 (latitude WGS84) | `GEO` | `null` |
| `geo_lng` | décimal | -180 à 180 (longitude WGS84) | `GEO` | `null` |
| `attachments` | tableau d'objets | voir format ci-dessous | `ATTACH` | `null` |

> `geo_lat` et `geo_lng` doivent être fournis **ensemble** — envoyer l'un sans l'autre retourne `400`.

#### Format `attachments`

```json
[
  { "url": "https://docs.example.com/agenda.pdf", "mime_type": "application/pdf" },
  { "data_base64": "<base64>", "mime_type": "image/png" }
]
```

Chaque objet doit avoir soit `url` (URL valide `http/https`) soit `data_base64`.
Le champ `mime_type` est optionnel mais recommandé.

---

### Exemple — créer un événement avec les nouveaux champs

```http
POST /calendars/42/events
Authorization: Bearer eyJ...
Content-Type: application/json

{
  "title": "Réunion de direction",
  "start_datetime": "2026-09-01T14:00:00",
  "end_datetime": "2026-09-01T15:30:00",
  "timezone": "America/Montreal",
  "priority": 1,
  "class": "CONFIDENTIAL",
  "transp": "OPAQUE",
  "categories": ["Direction", "Confidentiel"],
  "geo_lat": 45.5017,
  "geo_lng": -73.5673,
  "meeting_link": "https://meet.example.com/direction",
  "attachments": [
    { "url": "https://docs.example.com/ordre-du-jour.pdf", "mime_type": "application/pdf" }
  ]
}
```

---

### Réponse et export ICS

Ces champs sont :

- **Retournés** dans les réponses `GET /calendars/{id}/events/{eventId}`
- **Inclus** dans l'export `GET /calendars/{id}/ics` et les réponses CalDAV GET

Correspondance dans le fichier `.ics` généré :

```txt
CATEGORIES:Direction,Confidentiel
PRIORITY:1
CLASS:CONFIDENTIAL
TRANSP:OPAQUE
URL:https://meet.example.com/direction
GEO:45.501700;-73.567300
ATTACH;FMTTYPE=application/pdf:https://docs.example.com/ordre-du-jour.pdf
```

---

### Comportement de l'import ICS

Un fichier `.ics` importé via `POST /calendars/{id}/ics/import` mappe maintenant
automatiquement ces propriétés vers les colonnes correspondantes.

## Nouveautés (non cassantes) — Phase 3 : ATTENDEE, ORGANIZER, iTIP

### Champs disponibles sur `POST` et `PUT /calendars/{id}/events`

| Champ | Type | Description | Propriété ICS |
| :--- | :--- | :--- | :--- |
| `attendees` | tableau d'objets | Liste de participants RFC 5545 | `ATTENDEE` |
| `organizer_email` | string (email) | Email de l'organisateur (override du propriétaire) | `ORGANIZER` |
| `organizer_name` | string | Nom affiché de l'organisateur (CN) | `ORGANIZER;CN=` |

#### Format `attendees`

Chaque élément du tableau peut contenir :

```json
[
  {
    "email":    "alice@example.com",
    "name":     "Alice Tremblay",
    "role":     "REQ-PARTICIPANT",
    "partstat": "NEEDS-ACTION",
    "rsvp":     true,
    "cutype":   "INDIVIDUAL"
  }
]
```

| Sous-champ | Requis | Valeurs | Défaut |
| :--- | :--- | :--- | :--- |
| `email` | **oui** | adresse email valide | — |
| `name` | non | chaîne libre | — |
| `role` | non | `CHAIR` \| `REQ-PARTICIPANT` \| `OPT-PARTICIPANT` \| `NON-PARTICIPANT` | `REQ-PARTICIPANT` |
| `partstat` | non | `NEEDS-ACTION` \| `ACCEPTED` \| `DECLINED` \| `TENTATIVE` \| `DELEGATED` | `NEEDS-ACTION` |
| `rsvp` | non | `true` / `false` | `false` |
| `cutype` | non | `INDIVIDUAL` \| `GROUP` \| `RESOURCE` \| `ROOM` \| `UNKNOWN` | `INDIVIDUAL` |

> Un `attendee` sans `email` est rejeté avec `400`.

---

### Invitation automatique à la création

Quand un événement est créé avec des `attendees`, un email d'invitation est
automatiquement envoyé à chaque participant. L'email contient une pièce jointe
`.ics` avec `METHOD:REQUEST`, compatible Outlook, Gmail et Apple Mail.

---

### Nouvel endpoint — `POST /notifications/attendee-reply`

Permet d'enregistrer la réponse RSVP d'un participant (iTIP `METHOD:REPLY`).

```http
POST /notifications/attendee-reply
Authorization: Bearer eyJ...
Content-Type: application/json

{
  "event_id":      42,
  "attendee_email": "alice@example.com",
  "partstat":       "ACCEPTED"
}
```

**Réponse 200 :**

```json
{
  "success": true,
  "data": {
    "event_id":       42,
    "attendee_email": "alice@example.com",
    "partstat":       "ACCEPTED"
  }
}
```

**Erreurs :**

| Code | Cause |
| :--- | :--- |
| `400` | `partstat` invalide ou paramètre manquant |
| `403` | Appelant ni propriétaire de l'événement ni l'attendee concerné |
| `404` | Événement introuvable ou email pas dans la liste des attendees |

---

### Export ICS — correspondance Phase 3

```txt
ATTENDEE;CN=Alice Tremblay;ROLE=REQ-PARTICIPANT;PARTSTAT=NEEDS-ACTION;RSVP=TRUE;CUTYPE=INDIVIDUAL:mailto:alice@example.com
ORGANIZER;CN=Jean Organisateur:mailto:jean@example.com
```

L'export `GET /calendars/{id}/ics` et les réponses CalDAV GET incluent maintenant
ces propriétés quand les champs sont renseignés.

---

### Import ICS — correspondance Phase 3

Un fichier `.ics` importé via `POST /calendars/{id}/ics/import` mappe maintenant
les propriétés `ATTENDEE` et `ORGANIZER` vers les colonnes correspondantes.
Un `METHOD:REPLY` importé met à jour le `partstat` de l'attendee correspondant.
