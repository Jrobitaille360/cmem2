# cmem2 API — v2.12.0 — Notes client

Date : 2026-08-02

## BREAKING CHANGES

### 1. Politique de mot de passe unique — tous les mots de passe existants sont invalidés

Un seul jeu de règles s'applique désormais partout : **8 caractères minimum, une minuscule, une
majuscule, un chiffre, un caractère spécial**. Tous les hachages existants ont été invalidés :
chaque usager doit passer par « mot de passe oublié » à sa prochaine connexion par mot de passe.

Les comptes qui se connectent par code OTP ne sont pas concernés.

### 2. `POST /auth/send-code` — nouveau code `409` sur un compte en attente de suppression

Un compte supprimé mais pas encore effacé (délai de grâce de 30 jours) renvoie maintenant :

```json
{
  "success": false,
  "message": "Compte en attente de suppression définitive",
  "errors": {
    "error_code": "ACCOUNT_PENDING_DELETION",
    "purge_scheduled_at": "2026-09-01T02:14:07Z"
  }
}
```

Auparavant, l'API répondait `200` générique — et en pratique `500`, l'auto-inscription heurtant la
contrainte d'unicité sur l'adresse. **Les clients doivent traiter ce code** et proposer, s'ils le
souhaitent, le parcours de restauration.

### 3. `DELETE /users/me` peut désormais échouer avec `409`

Si un abonnement Stripe actif ne peut pas être annulé, la suppression est **refusée** :

```json
{ "success": false, "errors": { "error_code": "STRIPE_CANCEL_FAILED", "app_id": "cmemweb" } }
```

Aucun compte supprimé ne peut rester facturé. En fonctionnement normal (client qui annule d'abord,
ou annulation réussie côté serveur), le comportement est inchangé.

### 4. Un JWT émis avant une suppression de compte n'est plus accepté

Correctif de sécurité. Un jeton restait valide jusqu'à 15 jours après la suppression sur les routes
`/auth/*` — `GET /auth/me` retournait notamment le profil complet d'un compte supprimé. Ces appels
renvoient maintenant `401` `ACCOUNT_UNAVAILABLE`. Un changement de rôle prend également effet
immédiatement, sans attendre l'expiration du jeton.

## Nouveautés

### Suppression de compte conforme Loi 25

- `DELETE /users/me` renvoie `purge_scheduled_at` : date d'effacement physique (30 jours).
  Champ informatif — son absence ne remet pas en cause le succès de la suppression.
- **Restauration pendant le délai de grâce**, trois voies :
  - `POST /auth/restore-account` `{ email }` → code envoyé, réponse générique ;
  - `POST /auth/restore-account/verify` `{ email, code }` → compte restauré + JWT ;
  - une connexion réussie via `POST /auth/login` restaure aussi le compte.
- Après 30 jours, l'effacement est **irréversible** et l'adresse redevient disponible pour une
  inscription neuve, sans aucun reliquat.
- Un compte déjà purgé n'est jamais recréé par la voie de restauration : `404`
  `NO_ACCOUNT_TO_RESTORE`.

Périmètre effacé / conservé : voir la section « Suppression de compte et restauration » de
`docs/core/GUIDE.md`. Les registres de facturation Stripe sont conservés **anonymisés**
(obligation fiscale), sans aucun identifiant d'usager.

### Registre de modules activables — `/modules`

- `GET /modules` : liste des modules avec trois états — `available` (selon le plan), `enabled`
  (interrupteur usager), et quota serveur le cas échéant.
- `PATCH /modules/{key}` : activer ou éteindre un module. `403` `MODULE_NOT_AVAILABLE` si le plan
  ne le permet pas, `422` `UNKNOWN_MODULE_KEY` sur clé inconnue.
- Éteindre un module ne détruit aucune donnée : le rallumer restitue tout.

### Corbeille des fichiers — `GET /files/user/{user_id}?deleted=`

- `exclude` (défaut, comportement historique), `include` (actifs + supprimés), `only` (corbeille).
- Chaque ligne expose `deleted_at` et `accessibility`.
- Restauration par `POST /files/{id}/restore`.
- Sans le paramètre, la réponse reste celle d'avant.

## Sécurité — autres correctifs

- **Réinitialisation de mot de passe** : le code ne figure plus dans la réponse HTTP, passe à
  6 chiffres, limité à 5 tentatives par code et 5 demandes / 10 min.
- **Vérification de courriel** : le token ne figure plus dans aucune réponse HTTP, un seul token
  actif par usager, 5 tentatives maximum, réponse générique unique sur
  `resend-verification-email` (anti-énumération).

## Migration côté client

| Changement | Action requise |
| - | - |
| Politique de mot de passe | Aligner la validation locale sur 8 car. + maj/min/chiffre/spécial ; prévoir le parcours « mot de passe oublié » |
| `409 ACCOUNT_PENDING_DELETION` | Traiter le code sur `send-code` ; proposer la restauration si souhaité |
| `409 STRIPE_CANCEL_FAILED` | Afficher l'erreur sur l'écran de suppression de compte |
| `401 ACCOUNT_UNAVAILABLE` | Traiter comme une session expirée — déconnexion et purge des caches |
| `purge_scheduled_at` | Facultatif : afficher la date d'effacement |
