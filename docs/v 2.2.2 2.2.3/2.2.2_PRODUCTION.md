# Déploiement production — v2.2.2

Checklist à suivre dans l'ordre pour mettre en production la version 2.2.2.

> **v2.2.2 introduit le plugin Pomo (Phase 0 — prérequis système + Phase 1A — engagement MVP).**
> Une migration SQL est requise.

---

## 1. Migration SQL

### 1a. Plugin Pomo — table `pomo_engagements`

```bash
mysql -u <user> -p <database> < docs/pomo/migrations/001_pomo_engagement.sql
```

Ce script crée la table suivante :

| Table | Description |
| :--- | :--- |
| `pomo_engagements` | Inscriptions liste d'attente et réponses sondage (type, device_id, email, responses…) |

Structure complète :

| Colonne | Type | Nullable |
| :--- | :--- | :--- |
| `id` | `INT AUTO_INCREMENT PRIMARY KEY` | — |
| `type` | `ENUM('waitlist','survey') NOT NULL` | non |
| `device_id` | `VARCHAR(36) NOT NULL` | non |
| `email` | `VARCHAR(254) NULL` | oui |
| `responses` | `JSON NULL` | oui |
| `suggestion` | `TEXT NULL` | oui |
| `platform` | `ENUM('android','ios','web','windows','macos','linux') NULL` | oui |
| `language` | `VARCHAR(16) NULL` | oui |
| `app_version` | `VARCHAR(32) NULL` | oui |
| `build_number` | `VARCHAR(32) NULL` | oui |
| `session_duration` | `INT NULL` | oui |
| `network_status` | `ENUM('online','offline') NULL` | oui |
| `timestamp_utc` | `DATETIME NOT NULL` | non |
| `created_at` | `DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP` | non |

> La migration utilise `CREATE TABLE IF NOT EXISTS` — sans impact si la table existe déjà.

## 3. Déploiement du code

```bash
git fetch origin
git reset --hard origin/main
composer install --no-dev --optimize-autoloader
```

> `composer install` est requis — le namespace `Pomo\` a été ajouté à l'autoload PSR-4.

### Prérequis côté client

La v2.2.2 ne contient **aucun changement cassant**.
Les clients en v2.2.1 continuent de fonctionner sans modification.

Le nouvel endpoint est documenté dans `docs/v 2.2.2 2.2.3/2.2.2_CLIENT.md`.

```text
  → 422, { success: false, errors: [...] }

POST /pomo/engagement  (type=waitlist, email=invalide)
  → 422, { success: false, errors: [...] }

GET /health
  → 200  (core non impacté)
```

## Rollback

La migration est additive (`CREATE TABLE IF NOT EXISTS`).
Un retour au tag v2.2.1 ne nécessite pas d'annuler la migration —
la table `pomo_engagements` est ignorée par le code v2.2.1.

Si une annulation complète est nécessaire :

```sql
DROP TABLE IF EXISTS pomo_engagements;
```

Puis retour au code :

```bash
git reset --hard v2.2.1
composer install --no-dev --optimize-autoloader
```
